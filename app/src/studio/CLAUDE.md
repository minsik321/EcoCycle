# app/src/studio — 3D 홈

앱의 **유일한 3D 장면**이다. 홈 맨 위 전환에서 "3D"를 고르면 이 폴더를 lazy로 불러와 홈 화면 전체를 쓴다.
처음에는 "기본" 탭(`scene/`) 옆의 두 번째 탭 "스튜디오"로 **처음부터 새로** 만든 시안이었고, 목표는 **최대한의 시각 품질**이다.
2026-10-14 사용자 결정으로 기본 탭과 `scene/`을 지우고 이것만 남겼다(`docs/decisions.md` "기존 3D 장면 삭제").

## 창작의 자유 (이 폴더에서는 아래를 따르지 않는다)

이 탭은 다음 규칙에 **묶이지 않는다.** 이 폴더에서 작업할 때는 이 파일만 기준으로 삼고, 아래 문서의 시각·배치·성능 규칙은 무시한다.

- 기존 시각 디자인과 디자인 토큰(`styles/index.css`의 색·모서리·그림자, Tailwind 클래스, `components/common`의 패널·카드)
- 옛 장면(`scene/`, 삭제됨)의 세부 성능 원칙(저폴리·불투명 재질만·InstancedMesh 강제·카메라 ±35도 제한 등). 화질 3단계 자체는 따른다(고정 규칙 6)
- 루트 `CLAUDE.md`의 "범위를 벗어난 카메라 조작" 금지, `app/CLAUDE.md`의 화면 기준(태블릿 우선·48dp·호버 금지). 화면 우선순위는 고정 규칙 6을 따른다
- `app/src/features/CLAUDE.md`의 홈 배치 규칙(상단 카드 구성, 단계 바 구성, 정보 배치 기준)
- `docs/dashboard-spec.md`의 화면 모양·성능 원칙 절 (API·값 규칙은 그대로 따른다)

허용되는 것: 후처리(주변 차폐·빛 번짐·심도), 실시간 그림자, 환경광, 투명·유리 재질, 유리 UI, 입자, 자유로운 카메라 이동·확대·회전,
glTF 모델, 새 색·재질·배치·핀·패널. 기존 재질·팔레트·배치·핀·패널은 "정말 그게 최선일 때만" 다시 쓴다.
단, 이 연출은 `high` 단계의 모습이다. 휴대폰·태블릿에서는 고정 규칙 6에 따라 같은 장면을 가볍게 그린다.

## 고정 규칙 (이 탭에 남아 있는 규칙은 이것뿐이다)

1. **3D 없는 홈을 깨지 않고, 메인 묶음을 키우지 않는다.** 3D 코드는 `app/src/studio/`에만 두고, 3D를 고를 때만 lazy로 불러온다. 3D 없는 홈 화면은 three.js를 내려받지 않아야 한다.
   - `features/home`(과 앱 틀)이 정적으로 import해도 되는 것은 three를 import하지 않는 `three/stats.ts`(측정 화면)와 `preload.ts`(미리 받기·포스터 주소)뿐이다. 나머지는 `lazy(() => import('../../studio'))`만 쓴다. 스타일도 `studio.css`(패널 조각과 함께 내려받음)에만 둔다.
   - **조각은 둘이다:** 패널 조각(`index.ts` → LiveStudio·StudioView·overlay, three 없음, 약 16KB gzip)과 3D 조각(`StudioScene.tsx` → Stage·Director·three, 약 450KB gzip).
     패널은 store 값으로 바로 그려지고, 3D 장면은 첫 값이 그려진 뒤에 올린다(`SCENE_START`). 패널 쪽 파일은 three를 정적으로 import하지 않는다(`import type`만): 카메라 지역은 `world/views.ts`, 모델 목록은 `modelList.ts`.
   - 고친 뒤 `npm run build`로 처음 내려받는 묶음(index와 그것이 정적으로 import하는 조각의 합)과 패널 조각에 three가 없는지 확인한다(`loading.test.tsx`가 import 그래프를 본다).
2. **데이터는 기존 store·실시간 계층에서만 온다**(`/scene-demo`에서는 `demo/demoData.ts`의 예시 원본). 프론트에 업무 로직을 두지 않는다:
   번호판 → 회사 → 섹터 배정, 등급, 수분, 배합비, 압력은 서버 값이다. 서버가 아직 주지 않는 숫자가 필요하면 **명세와 모의 서버에 먼저 추가**하거나, 화면에 **"예시 데이터"라고 분명히 표시**한다.
3. **연결 끊김:** 연결이 끊기면 **모든 움직임을 멈추고** "연결 끊김"과 마지막 수신 시각을 보여 준다. 추측을 실제처럼 움직이지 않는다.
4. **조작:** 기존 조작 컴포넌트(`components/controls`)와 권한만 쓴다. 위험 조작은 기기 페이지에 둔다. 예외는 로봇 상세 패널의 운전 모드(`RobotModeControl variant="panel"`: 모드·섹터 지정·수동 집기/놓기, 기기 페이지와 같은 확인 단계·권한, 2026-10-16 사용자 요청)뿐이다. 비상정지처럼 보이는 버튼을 만들지 않는다.
   패널의 조작 영역(`.st-actions`)은 스튜디오의 단추 초기화에서 빠져 앱의 버튼 모양 그대로다.
5. **화면이 숨겨지거나 CCTV가 열리면 그리기를 멈춘다.**
6. **휴대폰 먼저, 그다음 태블릿, 그다음 데스크톱. 스튜디오도 화질 단계(high/standard/low)를 따른다**(2026-10-14 사용자 요청: 모바일이 주 대상).
   배치는 390×844(폰)에서 먼저 성립해야 하고 820×1180(태블릿)·데스크톱으로 넓힌다. 기본 단계는 모든 기기에서 `high`이고
   접속 때 프레임 측정 결과가 낮으면 그 단계로 내린다(2026-10-17). `low`는 끊김 없이 도는 것이 유일한 기준이다. 단계별 내용은 아래 "성능" 절.

이 여섯 가지는 `studio.test.tsx`, `loading.test.tsx`(조각 나누기·첫 화면·미리 받기·포스터), `features/home/switch.test.tsx`가 점검한다. 규칙을 건드리는 변경을 하면 그 테스트부터 본다.

## 미술 방향

고급스럽고 양식화된 아이소메트릭 "타이쿤 게임" 느낌의 물류 관제 화면. **시각 기준은 `docs/reference/`의 참고 프레임 10장**이다(모양·분위기만. 상표·아이콘·문구·데이터는 가져오지 않는다).
맞춘 내용과 이유는 `docs/decisions.md`의 "스튜디오 탭: 참고 화면에 맞춘 다듬기", 나란히 놓은 비교는 `docs/screenshots/studio/reference-match/`.

- **색·빛은 첫 시안(753041e)의 것**(2026-10-15 사용자 요청, `docs/decisions.md` "첫 스튜디오 시안의 색·빛으로 되돌리기", 비교는 `docs/screenshots/studio/restore-look/`): 채도 높은 파랑·노랑, 따뜻하고 분명한 해, 또렷하고 부드러운 그림자, 진한 주변 차폐.
- 밝고 깨끗하게, 그러나 **구역은 밝기 단계로 분명히 나뉜다**(2026-10-14 사용자 요청): 렌더 결과로 도로 회청색(#B9C2CE 근처, 흰 차선·가운데 점선) < 바깥 마당 콘크리트 옅은 회색(#E1E1E4 근처) < 건물 바닥 거의 흰색(#F4F4EF 근처, 칠한 통로선·노랑/파랑 바닥 표시). 해가 밝으므로 원색은 그보다 어둡다(마당 #B9BEC7, 아스팔트 #9AA5B4).
  가장자리에 초록 녹지 띠(#C3E4B4)와 풍성한 나무(숲도 맨땅도 아니게). 흰 벽 + 지붕선·모서리·문틀의 파랑 선(#2F6BFF), 벽 위 덮개·컨베이어 틀·압축기는 진한 파랑, 사무동 지붕은 옅은 회색(#D9DEE6).
  섹터는 칸막이 없는 노천 더미 둘(A·C): 더미 바닥에 등급 색(A 옅은 파랑 #E3ECFB, C 옅은 호박색 #FBEBD3) + 크라프트 파지 더미(높이는 서버 적재율).
  압축기 건물 지붕은 사진처럼 파랑(#4F8FE0, 옆동 #2F6FC4), 사무실 지붕은 짙은 회색, 북서쪽 숲은 짙은 녹지 + 나무.
  입고 트럭은 덤프 1 : 집게차 2(차량 ID 해시로 고정, `sim/grapple.ts`). 덤프는 노랑 운전석 + 은색·파랑·흰색 적재함, 회사마다 색 띠 하나(회사 이름은 서버 값, 이름 → 색은 `theme.ts`의 `companyStripe`), 지게차·로봇·작업자 조끼는 **안전 노랑**, 집게차는 파랑 운전석 + 운전석 뒤 노랑 너클 크레인·갈퀴 6개 집게, 상차 차량(서버 kind outbound)은 흰 운전석 + 25톤 카고(낮은 적재함, 상차 자리에서 옆판이 내려간다). 장면의 차량은 모두 서버 값이다(세워 둔 화물차·주차 차량 없음). 색은 `theme.ts`.
  현장 사진(2026-11-25) 재질: 사무실 짙은 회색 골판 2층(세로 골, 서쪽 1층 차양·큰 창·소화기, 동쪽 실외기, 남서 흰 창고), 압축기 건물 회색 벽 + 파란 지붕 + 지붕 위 파란 물탱크, 동쪽 블록 옹벽 + 쇠 난간, 북·남 높은 녹색 그물망, 남동 회색 철판 울타리, 도로변 전봇대·전선, 숲 쪽 높은 철 기둥, 부지 둘레 낮은 숲 언덕과 먼 산 능선.
  **전체 채도를 빼지 않는다.** 회색 화면은 연결 끊김에만.
- 빛: 따뜻한 해(2.6)와 또렷하고 부드러운 그림자 + 진한 주변 차폐. 노출을 올리면 밝은 바닥들이 같은 흰색으로 뭉개져 구역이 사라진다(두 번 겪었다: 빛을 바꾸면 렌더 결과 픽셀을 재서 확인하고, 모자라면 바닥 원색을 어둡게 한다).
- 카메라 거리 세 단계(`world/layout.ts`): **wide** 부지 전체(`WIDE_VIEW`, 바로 위에서 북쪽이 위인 `TOP_VIEW`), **mid** 한 구역(`AREAS`, 첫 번째가 기본 화면), **close** 고른 대상(`CLOSE_DISTANCE`). 처음에는 wide에서 기본 구역으로 들어온다. 좁은 화면에서 wide는 부지가 다 들어오게 더 물러나고(구역은 최대 1.3배), 안개 범위는 카메라 거리를 따라간다. 사진 방향 화면(`PHOTO_VIEWS`)은 눈높이(천정각 90도)·넓은 화각(`fov`)이고 패널 비켜 밀기를 위아래로는 하지 않는다. 점검 스크립트는 `__studioView`(바로 옮김)와 `__cameraError`(목표에 닿았나)로 찍는다. 카메라가 10m보다 낮으면(땅에서 보는 화면) 압축기 건물의 벽·지붕을 걷지 않는다. 먼 산 능선은 꼭대기가 땅보다 9~16m 위라 눈높이에서도 숲 위로 보인다. 핀끼리 겹치면 고른 핀 → 번호판 인식 → 가까운 핀 순으로 남기고 뒤 핀을 숨긴다(`Fx.tsx` `PinLayer`).
- 화면: 상단 바는 앱 전체의 상단 바 하나(`components/layout/TopBar`)를 3D 위에 띄운 것이다(2026-10-16 사용자 요청, 스튜디오가 앱의 모양을 쓰는 유일한 예외). 홈에서는 앱 틀의 바를 넘겨받아(`components/layout/shellChrome.tsx`) `LiveStudio`가 `overlay` 모양으로 그려 `StudioView`의 `topBar`로 넘기고, 시연 화면은 `DemoStudio`가 측정 버튼을 가운데 칸에 넣어 넘긴다. 자리만 `studio.css`의 `st-topbar`가 정한다(스튜디오의 단추 초기화는 바 안을 건드리지 않고, `low`에서는 바의 흐림도 끈다). 장면 검색은 없다(2026-10-16 삭제). 카메라 지역 전환은 바 밖, 지도 도구 곁의 작은 판(`st-area-dock`). 화면 이동은 앱의 주 메뉴 하나로 한다: 폰은 화면 아래 탭 바(3D 영역은 그 위에서 끝난다), 태블릿·데스크톱은 왼쪽 사이드바(다른 화면과 같은 폭·같은 접힘 상태, 펼치면 3D 자리가 그만큼 좁아진다). 바의 거리(`--st-gap`, 폰 8px·그 밖 10px)는 일반 화면의 떠 있는 바(`AppShell`의 `SHELL_GAP_*`)와 같아야 한다. 스튜디오 안에 메뉴를 따로 만들지 않는다(2026-10-15 사용자 요청).
- 패널: 성에 낀 흰 유리, 큰 모서리, 작고 가는 글씨, 카드마다 강조 숫자 하나, 상세 패널은 4~5줄 + "자세히", 표는 개수 붙은 탭 + 상태 알약.
- 선택 표시: 흰 알약 핀(상태 점 ✓ 또는 섹터 적재율 고리 + 이름 + 짧은 값, 아래에 가리키는 점), 고르면 파랑 칩. 멀리서와 폰 폭에서는 섹터 핀이 고리만. 선 상자, 굵게 퍼지는 고리, 고른 차량의 흐르는 점선과 목적지 3D 핀.
- 찰흙·장난감 같은 형태: 넉넉한 모서리 둥글림, 어디에나 부드러운 주변 차폐, 닿는 곳의 그림자, 부드러운 환경광.
- 눈이 가는 곳에 디테일: 트럭(운전석·창·거울·등·들리는 적재함·바퀴), 지게차(마스트·포크·머리 보호 틀·운전자), 형광 조끼 작업자, 로봇팔, 압축기(투입구·램·결속부·배출 받침대·베일 저울), 파지 더미가 쌓인 섹터 칸.
- 배치는 화면 폭 세 단계(`StudioView`의 `useLayout`), **폰부터** 맞춘다:
  - **폰(600px 미만, 기준 390×844)**: 앱 상단 바(로고 · 예시 · 3D/대시보드 전환 · 시각 · 사용자), 옆으로 미는 지표 칩 한 줄(오른쪽 끝을 흐리게 해 밀린다는 것을 알린다), 그 아래 3D가 화면 대부분, 왼쪽 위 지역 전환, 오른쪽 위 작은 지도 도구,
    아래 시트 하나(`PhoneSheet`: 기본은 접혀 공정 막대 + 요약 한 줄, 펼치면 배치 · 차량 · 섹터 · 베일 탭, 고르면 상세). 6단계 추적은 막대 + 지금 단계 이름만(`TrackerBar`).
  - **세로 태블릿(1000px 미만, 기준 820×1180)**: 지표 카드가 한 줄을 채우고, 상세 패널은 오른쪽, 표와 공정 추적이 아래에 쌓인다. 아무것도 고르지 않았을 때 배치 요약은 한 줄 칩(배치 번호 · 배합 · 현재 압력, `Detail`의 `collapsible`)으로 접혀 있고 누르면 펼친다(3D를 덜 가리게). 지역 전환은 지도 도구 오른쪽. 아래 표는 접기 단추로 요약 한 줄까지 접고(기기에 기억), 접힌 표는 공정 추적 바로 위에 붙는다.
  - **넓은 화면**: 상단 바, 지표 카드 3개(작은 추이선), 지도 도구, 오른쪽 상세 패널, 왼쪽 아래 6단계 공정 추적(입고 → 차량 인식 → 하역 → 배합 → 압축 → 출하, 둥근 아이콘을 선으로 잇고 오른쪽에 지금 대상 카드), 오른쪽 아래 탭 표(차량 / 섹터 / 배치 / 베일, 접기 단추로 요약 한 줄, 기기에 기억), 지표 카드 아래 왼쪽에 지역 전환.
  - 어느 폭에서도 패널끼리 겹치지 않는다(펼침 메뉴·시트를 펼친 때는 예외). 배치를 고치면 390×844와 820×1180에서 찍어 본다.
- 배치는 실제 부지의 위성사진(위가 북쪽)과 현장 사진 6장을 따른다(`docs/decisions.md` 2026-11-24 "실제 부지 배치와 섹터 2곳", 2026-11-25 "출차 계근·상차 차량을 서버 값으로, 현장 사진 기준 3D 다듬기"). 사진 좌표 → 월드는 `world/layout.ts`의 `sitePx` 하나(닮음 변환: 로봇이 원점, 사진의 레일 방향이 θc, **1px = 0.072**, 뒤집지 않음)로만 옮긴다.
  **축척(2026-11-26 S2k): 월드 1단위 = 2 m**(`M_PER_UNIT`, 실제 길이 → 월드는 `M(m)`). 부지 총면적 4,007 m²를 마당 포장 판(`PLATEAU` 안·사진 안·두 숲 밖, 약 193,000px²)의 넓이로 보면 1px = 0.144 m다(`layout.test.ts`가 넓이로 다시 잰다. 위성사진의 화물차 62.5px = 9.0 m, 계근대 66.9px = 9.6 m와 맞는다). 실제 크기 가정은 **`config/yard.ts`의 `REAL_SIZE_M` 한곳**(부지 면적, 베일 1.1 × 1.1 × 1.5 m·틈 0.1, 트럭 5톤급 7.5 × 2.4 m·운전석 2.9 m, 지게차 3톤급 폭 1.2 m, 작업자 1.75 m)이고 layout이 바꿔 쓴다: 베일 `BALE` 0.55 × 0.55 × 0.75, 트럭 `TRUCK` 3.75 × 1.2(모형은 축마다 `sx`·`sy`·`sz`배, 바퀴는 받침 그룹으로 둥글게 되돌린다), 지게차 `FORKLIFT_SCALE` 0.77(모형이 짧아 길이는 클램프까지 약 3.0 m, 사용자 확인), 클램프 `CLAMP_SCALE`(판 사이 = 베일 폭 × 1.06), 작업자 `WORKER_SCALE`. 압축기 통로(`BALER.halfX`, `BALER_TUNNEL`)·받침대·베일 저울(`YARD.scale.size`)도 베일에서 나온다. 위성사진의 베일 줄 간격(13.3px = 1.9 m)은 베일 크기와 맞지 않아 쓰지 않는다(전에는 이 간격에 맞춘 0.90 × 0.66 × 0.95, S2h의 트럭 1.1배·지게차 0.9배).
  **지형**: 마당과 계근대 단은 높이 0, 동쪽 도로는 낮고(북쪽이 가장 낮다) 남쪽으로 오른다(`roadY`, 바닥 높이는 `groundY`). 도로 쪽은 블록 옹벽 + 쇠 난간(`WALL_PX`)이고, 차는 **입구 경사로 한 곳**(`RAMP_PX`, 옛 입구 자리)으로만 드나든다. 입구를 막는 팔은 없다(차가 그대로 지난다).
  동쪽 도로, 사무실 바로 아래 계근대(동쪽 끝은 옹벽, 서남 끝에 번호판 인식 카메라 기둥), 그 아래 경사로, 가운데 콘크리트 마당(줄눈·얼룩은 바닥 텍스처 한 장 `three/floorTexture.ts`), 로봇 양옆의 큰 노천 더미 A(북서)·C(남동) — **레일 축에 거울 대칭**(`PILE_UW` 하나를 A는 (u, −w), C는 (u, +w)),
  로봇에서 남서쪽 압축기 건물로 오르는 경사 레일, 건물 안 **길쭉한 가로형 압축기**(뒤 유압 실린더 · 투입구 · 긴 압출 통로·결속부, 배출 롤러 없음), 남동 벽 배출구 뒤 **금속 받침대**(새 베일이 앞 베일을 한 칸씩 밀어낸다), 받침대 마당 쪽 **베일 저울**(무게 숫자 없음),
  베일 구역 둘(남동 ㄴ자: 울타리를 따라 이어진 4~5단 벽 — 지게차가 쌓는 칸 줄 11열과 그 뒤 한 줄·양 끝의 바탕 베일(`staticBaleCells('se')`), 칸 줄 앞이 지게차 길 — 과 북동 날개의 높은 벽, 북서 ㄱ자: 적치 재고), 북쪽 그물망 곁 베일 줄, 흩어진 파지 조각, 북서쪽 숲, 압축기 건물 남서·서쪽 뒤의 숲(`FOREST_SW`: 빈 포장 판을 덮는다, 사진에서는 이웃 땅). 도로변 전봇대는 도로 동쪽 가장자리 밖(`POLE_PX`), 마당 가로등 둘(`LAMP_PX`)은 트럭 길에서 0.5m 넘게 떨어진 곳(`layout.test.ts`가 모든 트럭 경로와 견준다). 흩어진 파지는 섹터 더미 둘레에만 두고 지게차 대기 자리·받침대·저울 앞에는 두지 않는다. 주차 차량·이웃 건물은 넣지 않는다.
- 전체 흐름 (서버 `stage`를 따르는 연출):
  - 입고 트럭: 도로(북쪽 밖) → 경사로로 올라 계근대 서쪽 앞에서 서쪽을 보고 선 뒤 **후진으로 계근대에 오른다** → **번호판 인식 장면**(계근대에 서기 전에는 서버 번호판이 와도 보이지 않고 서서 `PLATE_READ_SEC`(1초) 읽은 뒤 보인다, 카메라 빛줄기 + 핀 "입차 계근" · 서버 `plate`, 인식 전 "인식 중…", 입력 칸 없음, 인식되면 `PLATE_SHOW_SEC`(3.2초) 보여 준 뒤. 1.4초일 때는 눈에 띄지 않았다, S2i #4) → **앞으로 내려가** 배정 더미 앞 후진 자리에 선 방향 그대로 후진해 원호 하나로 쏟는 자리에 든다(A는 북쪽으로 올라섰다가 남→남서 45°, C는 서쪽을 보고 섰다가 동→남→남서 135°, 2 m마다 60° 넘게 돌지 않음. S2k: 전에는 후진 구간 안에서 앞뒤로 오가 방향이 180° 튀었다. `unloading`에만 적재함을 든다. 집게차는 받침다리를 내리고 크레인으로 1~4회 집어 섹터에 떨어뜨린 뒤 접는다: 남은 하역 시간(`config/yard.ts` `UNLOAD_EXPECTED_SEC` 가정)에 맞춰 횟수를 줄이고, 다 접어야 떠난다) → `weighing_out`에 **앞으로 계근대에 올라** 동쪽을 보고 다시 잰다(인식 장면 "출차 계근") → **후진으로 서쪽에 내려와** 경사로 위 출차 대기 자리(`EXIT_HOLD`, 도로 쪽을 봄)에서 기다린다 → `departed`(회사 밖)가 오면 **경사로를 내려가 도로 남쪽 차로를 따라 사진 남서쪽 밖 도로 끝까지 달려 나간 뒤 빠진다**(`EXIT_LEAVE`, 2026-11-26 S2i #7: 그 자리에서 사라지지 않는다). 장면이 늦어 출차 계근 전에 `departed`가 오면 하던 동선(출차 계근까지)을 마친 뒤 같은 길로 나간다. 나가는 차(`leaving`)는 회사 밖이라 표의 "차량 N"에 세지 않는다(`truckCount`). 드물게 나가는 차가 길에서 6초 넘게 막히면(하역 없이 출차한 차와 상차 차가 서로 막는 경우) 그때만 뺀다. 아직 도로에서 들어오지 않은 차(부지 밖)는 바로 뺀다. 출차 계근 → 출차의 동선은 첫 구간이 차가 보던 방향 그대로라 한 걸음 사이에 자리·방향이 튀지 않는다(`sim/exit.test.ts`).
  - 상차 차량(`kind: "outbound"`, 25톤 카고 12 m, 계근대 14 m): 같은 입구 → 계근(`arrived`·`identified`) → 마당 가운데 상차 자리(`HOLD`, 옆판을 내린다) → `loading`·`loaded` 동안 지게차가 북서 맨 위 베일을 하나씩 꺼내 돌려 잡기 자리에서 90° 돌려 잡고 차의 양쪽(서쪽 곁은 바로, 동쪽 곁은 차 앞을 돌아)에서 싣는다(5열 × 2줄 × 2단 = 20자리, 아래 단 먼저. 실은 수 = 서버 `baleIds` 수, 이미 상차 중인 차는 그만큼 실린 채 놓는다). 지게차는 북서 길에서 마당 차례를 한 번 놓아 기다리는 입고 트럭에 양보한다. `weighing_out`이 와도 서버가 실었다고 한 베일을 다 싣기 전에는 떠나지 않고(최대 `LOAD_WAIT_SEC`, 막힌 지게차는 `abortLoad`로 끝냄), 옆판을 올리고 물렸다가 앞으로 계근대에 올라 잰다 → 후진으로 내려와 출차 대기 자리 → `departed`에 입고 트럭과 같은 길로 나간 뒤 빠진다(실린 베일은 차를 따라가고 차와 함께 빠진다). 서버 값 없이 시간으로 만드는 상차 차량은 없다.
  - 베일(`sim/yard.ts`): 배출 → 받침대(끝에 닿은 베일만 지게차가 집는다) → 저울에 두 개를 위아래로 겹쳐 내려놓고 집게만 벌렸다가 다시 집어 바로 옮김(한 번에 잼) → 남동 칸 줄에 한 쌍씩(4단) → 남동의 빈 열이 모자라면 **가장 오래된 열부터 줄 단위로 북서**로 → 서버 `shipped`는 북서에서 하나가 빠진다(그 베일이 남동에 있으면 이름 없는 재고가 되고 북서 맨 위가 빠진다. 상차 자리의 차에 실린 것이면 지게차가 북서에서 꺼내 싣는다). 처음 열 때 남동·북서에는 이름 없는 재고(숫자·이름 없음)가 쌓여 있다. 정돈: 모두 같은 방향·같은 간격(칸 줄 축), 무작위 회전 없음.
  모두 스스로 움직이고 서로 비켜 간다(트럭은 `TRUCK` 외곽선으로 앞을 살핀다). 경사로·계근대·그 서쪽 앞마당은 "계근대 차례", 마당 안쪽 길·지게차가 가로지르는 길·북서 길은 "마당 차례"(`sim/token.ts`)를 잡은 하나만 움직인다. 트럭은 계근대에 오른 뒤 갈 곳(더미 앞·대기 자리·상차 자리)이 있을 때만 경사로로 들어오고, 출차 계근을 기다리는 차가 먼저다. 회사 안 차량(서버 `departed` 아님)은 몇 대든 모두 장면에 그린다(트럭 칸·모형은 모자라면 늘린다, 상한 없음. 도로에 줄 선다): 장면의 회사 안 트럭 대수(`truckCount`, 출차해 나가는 차 제외) = 표의 "차량 N"(`traffic.test.ts`는 매 걸음, `yardSoak.mjs`는 같은 값을 받은 표본마다 한 번도 어긋나지 않아야 한다).

## 값과 연출의 경계 (고정 규칙 2·3을 지키는 방법)

- **서버 값:** 기기 상태, 요약(오늘 베일·평균 수분·가동률), 추이(`GET /plant/history`), 차량·배치·베일의 단계와 값, 알람, 연결 상태. 패널·핀·표는 이 값을 그대로 적는다.
- **연출:** 트럭·지게차·작업자가 "어느 길로 얼마나 빨리" 움직이는지, 쏟아지는 파지, 램의 왕복, 점선. 서버 센서 값이 아니고 화면에 숫자로 쓰지 않는다.
  연출은 서버 단계가 정한 목표까지만 간다(인식 전에는 계중대에서 기다리고, 하역 단계가 와야 적재함을 든다, 출하 단계가 와야 지게차가 싣고 나간다).
- 처음 본 대상이 이미 진행 중이면 지나간 장면을 지어내지 않고 있어야 할 자리에 바로 놓는다. 이미 끝난 대상(출차한 차량, 출하된 베일)은 만들지 않는다.
- **월드 시계:** 모든 움직임은 `Director.step()`이 돌리는 시계 하나를 쓴다. 끊기면 Pacer(`sim/pace.ts`)가 `step`을 부르지 않으므로 전부 멈춘다. 고리·점선·깜빡임도 이 시계를 쓴다.
  새 움직임을 넣을 때 `performance.now()`나 r3f의 시계를 직접 쓰지 않는다(끊겨도 움직이게 된다). 카메라만 예외다(끊긴 화면도 둘러볼 수 있어야 한다).
- 끊긴 동안에는 `Director.sync()`도 부르지 않는다. 복구되면 store가 REST로 다시 받은 상태가 들어와 이어진다.
- 로봇이 집는 자리·놓는 자리는 서버 관절 값(base 각도)에서 나온다. 섹터 더미와 레일은 그 자리에 맞춰 놓였다(`world/layout.ts`의 `PICK`, `PLACE`). 로봇 배율을 바꾸면 더미 윤곽(`PILE_PX`)도 함께 봐야 한다.

- 트럭·지게차·작업자·나무·소품·건물은 코드로 만든 모형이다. 이유: 적재함·포크·팔다리가 따로 움직여야 하는데, CC0 팩 하나로 이 전부를 갖추면서 마디가 나뉜 것을 찾지 못했다.
- 모델을 다시 쓰게 되면: 파일은 `app/public/models/<팩 이름>/`에 라이선스 파일과 함께 두고, `MODELS`에 파일·배율·회전·원점·라이선스·출처·삼각형 수를 적는다(목록에 없는 파일은 쓰지 않는다).
  팩은 하나로 통일하고, 모델 파일을 못 받아도 화면은 완성되어 있어야 한다(코드 모형을 먼저 그리고 파일이 오면 바꾼다). Meshopt 압축을 쓰고, Draco 모델은 `draco: true`로 적어 처음 불러올 때만 디코더를 받게 한다
  (`app/vite.config.ts`의 `dracoOnce`가 three의 DRACOLoader를 glTF용 디코더 한 벌만 가리키게 바꿔 둔다).

- **필요할 때만 그린다**(`frameloop="demand"`): Stage의 Pacer가 화면 주사마다 `sim/pace.ts`를 부른다. 단계의 상한 간격마다 월드 시계를 한 번 돌리고, `Director.motionKey()`가 바뀌었거나
  깨우개(`three/motion.ts`: 카메라가 아직 목표에 닿지 않음, 로봇 관절 값이 마지막으로 그린 자세와 다름, 고른 대상의 고리·점선, 경보등)가 부를 때만 `advance()`로 바로 한 장 그린다.
  아무것도 움직이지 않으면 그리지 않는다(끊긴 동안 5초에 0장, 측정). 작업자의 제자리 몸짓처럼 시계만 따르는 장식은 깨우지 않는다(다른 것이 움직일 때 함께 움직인다).
  새 움직임을 넣으면 `motionKey()`에 넣거나 깨우개를 단다. 넣지 않으면 그 움직임은 다른 것이 움직일 때만 보인다.
- Stage는 `memo`다. 패널이 1초마다 다시 그려져도 무대를 다시 그리지 않게(r3f는 새 배열 props를 바뀐 값으로 보고 한 장을 더 그린다).
- **시작(폰 먼저, 2026-10-15):** 목표는 로그인 뒤 1.5초 안에 지표가 보이는 것. 순서:
  1. 로그인 화면: 홈을 3D로 기억했고 데이터 절약·2G가 아니면, 한가할 때 3D 파일을 미리 받는다(`features/home/useStudioPrefetch` → `preload.ts`). JS 조각은 `modulepreload`(받고 읽기만, 실행 안 함. 받는 중에 로그인해도 `import()`가 이어 쓴다), CSS·모델·포스터는 `prefetch`. **정적 파일만** 받고 API·WebSocket은 부르지 않는다. 조각 이름은 빌드가 `index.html`의 `<meta name="ecocycle-studio-files">`에 적는다(`vite.config.ts`의 `studioFilesMeta`, 개발 서버에는 없음).
  2. 로그인 뒤 홈: 패널 조각(작음)만 받아 패널을 store 값으로 바로 그린다. 그 아래에 준비 화면(빈 장면 포스터 + 옅은 성에 막 + 돌림표 + "3D 장면을 준비하는 중…", z 5, 누르기를 막지 않음). 핀은 첫 장 뒤에 놓는다. 패널이 뜨면 3D 파일 받기를 시작한다(이미 받았으면 그대로).
  3. 첫 값(요약)이 그려진 다음 3D 장면을 올린다(`SCENE_START.waitMs`: 값이 오지 않으면 2.5초 뒤 그냥 올림, 끊긴 채 열면 바로). 장면 만들기가 느린 폰의 메인 스레드를 수 초 잡기 때문이다.
  4. 셰이더를 `renderer.compileAsync`로 미리 컴파일하고 첫 장을 그리면 준비 화면을 걷는다.
- 포스터(`app/public/studio/poster-wide.jpg`, 세로 화면은 `poster-tall.jpg`)는 로그인 전에 받는 공개 파일이다: **빈 장면만**(데이터 없음, 로봇 기본 자세, 번호판·회사 이름·숫자·패널·핀 없음). `npm run poster`(`scripts/poster.mjs`, `/scene-demo?poster=1`)로 찍고, 화면에 글자가 있으면 멈춘다. 장면이 크게 바뀌면 다시 찍는다.
- 첫 화면 시간 측정: `npm run measure:load`(`scripts/loadtime.mjs`): 프로덕션 빌드를 배포처럼(gzip, 다시 확인 캐시) 내주고 390×844 폰, 4G(4Mbps·150ms), CPU 4배 느림으로 로그인 → 지표 숫자, 로그인 → 3D 첫 장을 잰다. 결과는 `docs/decisions.md`.
- **low는 같은 배치를 가볍게 그린다**(`buildWorld(lite)`, `Piles lite`): 나무 공 하나·성긴 숲, 언덕·능선 분할 낮춤, 바탕 베일 띠 없음, 파지 조각 절반, 더미 조각은 둥글리지 않은 상자. 쏟는 파지는 쏟는 트럭에만 칸을 준다(최대 4대). 2026-11-25 측정(프로덕션 빌드, GPU + CPU 4배 느림, 기준 cfff539와 같은 데이터 스냅샷 `/scene-demo?snapshot`): low는 1440·820·390 모두 초당 30장(상한), 화면 갱신 간격 최대 26.8ms·50ms 넘는 멈춤 0번(기준도 같음), 삼각형 43만(기준 40만). 패널 쪽 매초 멈춤을 줄였다: 시각 글자 캐시(`Panels.tsx`), 시연 측정 글자는 작은 조각(`DemoStudio`의 `DrawStats`), 숨은 트럭 모형은 행렬 갱신을 건너뛴다.
- 반복물은 합친 메시(`Kit`): 베일 블록·그물망·울타리·난간·전봇대·전선·나무·언덕·파지 조각은 재질별 메시 몇 개에 들어가 그리기 횟수가 늘지 않는다. 줄눈·얼룩은 텍스처(판 하나).
- 측정 화면: `/scene-demo`(3D 홈만, 예시 데이터). 상단 바에 그린 장 수(지금·평균·최저), 메모리, 기기 종류·단계(측정값), 첫 화면까지 걸린 시간, 그리기 횟수·삼각형 수. 측정값과 묶음 크기는 `docs/decisions.md`.

## 글 줄바꿈

- 앱 전체 규칙(`styles/index.css`: 한국어 낱말 단위 줄바꿈, 이름표·탭·버튼 한 줄)을 따르고, 패널 쪽 규칙은 `studio.css` 끝의 "글 줄바꿈" 절: 이름·값 줄(`.st-rows`)은 같은 기준선에 값은 말줄임, 알약·칩·탭은 한 줄, 표는 첫 칸만 줄어들며 말줄임, 폰 시트의 표는 좁으면(컨테이너 380px 이하) `st-col-opt` 칸(차량의 섹터, 섹터의 막대, 배치의 목표 압력)을 뺀다.
