## 2026-10-13 프로젝트 폴더 구조 초안

## 2026-10-13 언어·도구 선택

## 2026-10-13 테스트·차트: Vitest + Recharts

## 2026-10-13 이력 그래프 표시 방식: 구간 단위 넘기기
- 결정: 기기 페이지 이력 그래프는 한 번에 한 구간만 요청해서 그린다. 처음에는 최근 하루(10분 간격)를 보여 주고, 단위를 바꾸면 그 단위로 다시 요청하고, 과거는 스와이프나 `◀ 이전 / 다음 ▶`으로 구간을 통째로 넘겨 새로 요청해 그린다.
- 이유: 그래프는 센서값을 그때그때 보는 용도라 상세할 필요가 없다. 구간마다 점이 수백 개 이하로 유지되어 Recharts로 충분하다. 연속 가로 스크롤은 과거 데이터를 앞에 붙일 때 스크롤 위치가 튀고 Recharts가 끄는 동작을 기본 지원하지 않아 구현 비용이 크다. 명세의 `GET /devices/{id}/history?from&to&interval`을 그대로 쓴다.

## 2026-10-13 배포 방식: 프로토타입은 Vercel + Render, 이후 Capacitor APK
- 결정:
  - 프로토타입: 프론트(`app` 빌드 결과, 정적 파일)는 Vercel, 목서버(`mock-server`, Node)는 Render에 올린다. 대표님은 태블릿 브라우저로 Vercel 주소에 접속한다.
  - 이후: 같은 프론트 코드를 Capacitor로 감싸 안드로이드 APK로 배포한다(APK 직접 설치 또는 Firebase App Distribution). Vercel 웹 버전은 대안 배포(PWA)로 남긴다.
  - 실서버가 준비되면 목서버를 내리고 프론트의 서버 주소(`VITE_API_BASE`, `VITE_WS_BASE`)만 실서버로 바꿔 다시 빌드·배포한다. 실서버 배포는 서버 담당 몫이다.
- 이유: 실서버가 없는 상태에서도 실제와 같은 REST·WebSocket 경로로 프로토타입을 보여 주고 검증할 수 있다. 프론트는 정적 파일이라 웹 호스팅과 APK에 같은 코드를 쓴다. 나중에 실서버로 옮길 때도 "주소 변경 후 재빌드"라는 같은 절차를 따른다.
- 주의:
  - Render 무료 요금제는 접속이 없으면 잠들어 첫 접속이 느리다. 시연 전에 한 번 열어 깨운다. 재시작하면 목서버 데이터는 처음 상태로 돌아간다.
  - `VITE_*` 값은 빌드 시점에 들어가므로 바꾸면 Vercel 재배포·APK 재빌드가 필요하다.
  - react-router 경로 새로고침용으로 `vercel.json`에서 모든 경로를 `index.html`로 돌린다.
  - 목서버 CORS에 Vercel 주소를 허용하고, APK 단계에서는 Capacitor 앱 주소도 추가한다.
  - 두 주소 모두 공개되므로 회사명·실제 설비 정보는 넣지 않고, 테스트 계정 비밀번호는 실제로 쓰는 것과 다르게 둔다.
- 상태: 확정 (2026-10-13 사용자 확인)


## 2026-10-13 비동기 요청은 createAsyncThunk로 통일
- 결정: store의 비동기 요청(로그인, 명령 전송)은 RTK Query 대신 `createAsyncThunk`로 쓴다.
- 이유: 서버 값은 대부분 WebSocket으로 밀려 오고 REST는 재동기화·이력 조회·명령에만 쓰여서 RTK Query의 캐시·재요청 기능이 거의 필요 없다. 의존성과 개념이 늘지 않는다. 이력 그래프처럼 화면에서만 쓰는 조회는 store에 넣지 않고 화면의 훅에서 api를 직접 부른다.
- 상태: 확정

## 2026-10-13 api·realtime은 store를 import하지 않는다 (의존 방향)
- 결정: `api`와 `realtime`은 `store`를 import하지 않고, 값은 콜백/인터페이스로 내보낸다. `api`는 `setAuthLostHandler`, `realtime`은 `RealtimeSink`를 받고, `store`가 이를 구현해 연결한다(`store/realtimeSink.ts`, `store/bootstrap.ts`). 실시간 연결을 켜고 끄는 `useRealtime`도 `realtime/`이 아니라 `store/`에 둔다.
- 이유: 원래 구조도(`api, realtime ─► store`)는 실시간·REST 코드가 store에 묶여 단위 테스트(가짜 타이머, 가짜 소켓)가 어렵다. 방향을 뒤집으면 순환 없이 각 계층을 따로 테스트할 수 있다.
- 상태: 확정

## 2026-10-13 리프레시 토큰은 웹에서 메모리에만 둔다 (프로토타입)
- 결정: 리프레시 토큰의 기본 저장소는 메모리다. 웹 프로토타입에서는 새로고침하면 다시 로그인해야 한다. 안드로이드 앱에서는 Capacitor 보안 저장소 구현을 `setRefreshTokenStore`로 끼운다.
- 이유: "토큰을 URL·localStorage에 두지 않는다" 규칙. 웹에서 로그인을 유지하려면 `sessionStorage` 등 브라우저 저장소가 필요한데 규칙과 충돌한다.
- 상태: **대체됨** (2026-10-15 "자동 로그인" — 웹은 HttpOnly 쿠키, 안드로이드는 보안 저장소)

## 2026-10-13 CCTV 재생: hls.js를 필요할 때만 불러온다
- 결정: `<video>`가 HLS를 직접 재생하는 기기(안드로이드, 사파리)는 주소를 그대로 쓰고, 못 하는 기기(데스크톱 Chrome 등)에서만 `hls.js`를 동적 import로 불러온다. WebRTC 주소는 아직 지원하지 않고 안내만 한다.
- 이유: 명세는 앱이 서버가 변환해 준 주소를 `<video>`로 재생하기만 한다고 정했다. 안드로이드 태블릿 실사용에서는 기본 재생으로 충분하지만 개발·시연(데스크톱 브라우저)에서는 hls.js가 필요하다. 동적 import라 CCTV를 열기 전에는 번들에 영향이 없다.
- 상태: 확정 (WebRTC는 서버가 제공하면 추가: docs/questions.md B8)

## 2026-10-13 화질 모드는 기기에 기억한다

- 이유: 기기마다 성능이 달라 기기 단위 설정이다. 토큰 같은 비밀이 아닌 표시 설정이라 "토큰을 localStorage에 두지 않는다" 규칙과 무관하다. 저장소를 쓸 수 없으면 기본값으로 동작한다.

## 2026-10-13 연결됨(online)은 첫 메시지를 받았을 때, 끊긴 동안 마지막 관절 자세는 남긴다
- 결정: WebSocket이 열린 것만으로는 `online`으로 바꾸지 않고, 새 연결의 첫 메시지를 받았을 때 `online`으로 바꾸고 REST로 맞춘다(재동기화). 관절 버퍼도 그때 비운다. 끊겨 있는 동안(재연결 시도 포함)에는 마지막 자세를 버퍼에 남겨 둔다.
- 이유: 통합 점검(`disconnect` 시나리오)에서 두 가지가 드러났다. ① 서버가 연결은 열어 두고 침묵하면 소켓이 열리는 순간 "연결됨"으로 보였다. ② 재연결 시도 때 버퍼를 비워서 3D 로봇팔이 멈춰 있을 마지막 자세가 사라졌다. 명세의 "끊기면 마지막 값을 정상처럼 보여 주지 않고 로봇팔은 멈춘다"에 맞춘다.
- 상태: 확정

- 결정(앱 전체, `styles/index.css`): `html { word-break: keep-all; overflow-wrap: break-word }`. 이름표·표 머리·탭·버튼·상태 글은 한 줄(`white-space: nowrap`), 상태 알약은 줄지 않음. 이름·값 줄은 같은 기준선 + 고정 폭 숫자, 값이 길면 한 줄 말줄임. 3D 홈 패널은 `studio.css` 끝의 "글 줄바꿈" 절(이름·값 줄, 알약·칩·탭 한 줄, 표 첫 칸만 말줄임, 폰 시트 표는 좁으면 덜 중요한 칸을 뺌).
  - `overflow-wrap: anywhere`(요청안)가 아니라 `break-word`로 했다: anywhere는 상자의 최소 폭 계산을 바꿔 표 칸·flex 항목이 한 글자 폭까지 줄어들 수 있고, 실제로 관절 표의 숫자가 그렇게 갈라졌다. break-word는 넘칠 때만 끊고 상자를 줄이지 않는다.

## 2026-10-15 자동 로그인: 웹은 HttpOnly 쿠키, 안드로이드는 보안 저장소 (localStorage 아님)
- 결정: 로그인 화면에 "자동 로그인" 확인란(기본 끔)을 둔다. 리프레시 토큰은 웹에서는 서버가 심는 쿠키(`ecocycle_rt`: HttpOnly, Secure, `Path=/api/v1/auth`, 같은 사이트 `SameSite=Lax`, 다른 사이트 `None` + `Partitioned`)로, 안드로이드에서는 본문으로 주고받아 Android Keystore 기반 보안 저장소에 둔다. 켜면 웹 14일 지속 쿠키·앱 보안 저장소, 끄면 웹 세션 쿠키(브라우저를 닫을 때까지)·앱 메모리. 액세스 토큰은 계속 메모리에만 둔다. 앱 시작 때 리프레시 → `GET /me`로 세션을 되살리고 그동안 "로그인 확인 중…"을 보인다. 리프레시할 때마다 토큰을 교체하고 이미 쓴 토큰이 오면 그 세션 전체를 폐기한다. 명세 6절 "토큰 보관과 자동 로그인"에 반영했다.
- 이유:
  - localStorage·sessionStorage는 같은 페이지의 어떤 스크립트든 읽을 수 있어 XSS 한 번이면 리프레시 토큰(장기 자격)이 통째로 빠져나간다. HttpOnly 쿠키는 스크립트가 읽을 수 없고, `Path`를 인증 경로로 묶어 다른 API 요청에는 실리지도 않는다. 기존 규칙("토큰을 URL·localStorage에 두지 않는다")을 지키면서 새로고침을 견디는 방법은 이것뿐이다.
  - 쿠키는 CSRF를 부르므로 `SameSite`, CORS의 명시한 출처 목록(`credentials: true`에서는 `*` 불가), 쿠키 요청의 `Origin` 확인, JSON 본문(사전 요청 유발)으로 막는다. 쿠키로 얻는 것은 액세스 토큰뿐이고 그 응답은 허용한 출처만 읽을 수 있다.
  - 안드로이드 WebView(Capacitor)는 API와 출처가 달라 쿠키가 불안정하고, 기기에 Keystore라는 더 나은 보관소가 있다. 그래서 같은 API에 `refreshTokenDelivery: "body"`로 주고받는다. 앱 코드는 `api/tokens.ts`의 `RefreshTokenStore` 하나에 웹(`createCookieTokenStore`, 기본)·네이티브(`createNativeTokenStore`) 구현을 둔다.
  - 교체 + 재사용 감지: 토큰이 새어도 정상 사용자와 훔친 사람 중 늦게 쓴 쪽에서 재사용이 드러나 세션이 끊긴다. 계정이 역할별로 공유되므로(admin·operator·viewer) 계정 전체가 아니라 그 로그인 세션만 폐기한다.
  - 여러 탭이 같은 쿠키로 동시에 리프레시하면 재사용으로 오인되므로 웹은 Web Locks로 탭 사이 리프레시를 한 번에 하나만 보낸다.
- 주의:
  - Vercel + Render처럼 앱과 API가 다른 사이트면 `SameSite=None`(모의 서버는 `REFRESH_COOKIE_SAMESITE=none`)이 필요하고, Safari처럼 제3자 쿠키를 막는 브라우저에서는 웹 자동 로그인이 동작하지 않을 수 있다(로그인 화면으로 돌아갈 뿐 안전에는 문제없음). 실서버는 앱과 같은 사이트(예: `app.`·`api.` 하위 도메인)에 두기를 권한다.
  - `Secure` 쿠키라 `http://localhost`는 되지만 태블릿에서 `http://192.168.x.x`처럼 HTTP LAN 주소로 열면 쿠키가 저장되지 않는다(자동 로그인만 안 되고 로그인은 된다).
  - 모의 서버는 `CORS_ORIGINS`가 비어 있으면 `http://localhost:5173`, `http://127.0.0.1:5173`만 허용한다(전에는 모든 출처). 다른 주소로 열면 `CORS_ORIGINS`에 넣는다. 안드로이드 앱 단계에서는 WebView 출처도 넣는다.
  - 보안 저장소 플러그인은 아직 고르지 않았다(Capacitor 미설치). 안드로이드 빌드 단계에서 Android Keystore로 암호화하는 플러그인을 골라 `SecureStorage`(get·set·remove) 모양으로 감싸 `setRefreshTokenStore(createNativeTokenStore(...))`로 끼운다.
  - 앱 시작 때 서버에 닿지 못하면 토큰을 지우지 않고 "다시 시도 / 로그인 화면으로"를 보인다(네트워크·5xx로는 로그아웃하지 않는다는 기존 규칙). 거부(4xx)면 안내 없이 로그인 화면, 사용 중 거부면 기존처럼 "로그인 시간이 지나 다시 로그인해야 합니다" 안내.

## 2026-10-15 배치·베일 수동 제어 (5단위)
- 결정: 지금·다음 배치를 사람이 바꿀 수 있게 하고, 베일은 만들어질 때의 값을 따로 남긴다. 화면은 `/records/batches`(`BatchBalePage`: 현재 배치 요약, 현재/다음 선택, `BatchControls`, 사건 `RecordList`), 배치 상세 `/records/batches/:id`, 베일 상세 `/records/bales/:id`(`BaleDetailPage`).

  - 배합·압력 검사: 화면은 입력 초안만 검사해 버튼을 막는다(배합은 섹터마다 0~100%이고 합계가 정확히 100%, 압력은 서버가 준 `pressureRange` 안의 숫자, 건너뛰기 사유는 공백 빼고 1~120자). 최종 판정은 서버가 실행할 때 다시 한다: 섹터 중복·합계 오류·쓸 수 없는 섹터(제외·빈 섹터)·압력 범위 위반·이미 끝난 배치·이미 정지/재개된 상태는 `command.result` rejected, 구조 오류·확인 누락은 422. 배합은 로봇이 첫 집기를 올리기 전까지만, 목표 압력은 압축을 시작하기 전까지만 바꿀 수 있고, 압축 중에는 건너뛸 수 없다. 압축기가 꺼졌거나 알람이면 배치 명령을 모두 거부한다. 허용 압력 범위(목업 27.0~30.0 MPa)는 서버 fixtures 값을 `GET /batches/control`로 받는다.
  - 서버 확정값과 초안을 나눈다: "서버 확정 배합·목표"는 `GET /batches/control` 값(2초마다 조회하고, 명령 결과가 오거나 다시 연결되면 바로 다시 조회)이고, 입력칸 값은 적용 전 초안이다. 결과가 오기 전에는 표시값을 바꾸지 않는다.

  - 배치–베일은 1 → N이다: 배치는 `baleIds[]`, 베일은 `batchId`를 가진다. 목업은 배치 하나에 베일 하나만 만들지만 화면·타입은 여러 개를 전제로 그린다. 베일 상세(`GET /bales/{id}`)는 생산 당시 압력·평균 수분·배합 스냅샷과 적치/출하 상태를 담는다. 나중에 배치를 바꿔도 이미 만든 베일의 기록은 바뀌지 않는다.

- 이유: 기존 압축기 명령 경로를 쓰면 멱등 키·서버 권한 검사·결과 추적을 새로 만들 필요가 없다. `batchId`를 넣어야 "지금 압축기가 하는 배치"가 바뀌어도 엉뚱한 배치에 적용되지 않는다. 투입·압축을 시작한 뒤에 바꾸면 실제 베일과 기록이 어긋나므로 막는다. 베일을 스냅샷으로 남겨야 출하 뒤에도 그 베일을 어떤 조건으로 만들었는지 되짚을 수 있다.

## 2026-10-16 기록 상세는 팝업, 이력 깊이 1
- 결정: 차량·배치·베일 상세는 페이지를 옮기지 않고 지금 화면 위의 팝업(모달)으로 연다. 폰은 아래 시트(길면 화면 높이 전체), 640px 이상은 가운데 대화상자(베일은 좁게). 배경은 옅게 어둡고 닫기 버튼이 있으며 Esc·바깥 누르기·뒤로 버튼(브라우저·안드로이드)도 닫기와 같다. 여는 곳: 공정 기록의 차량·배치·베일 탭 줄, 배치·베일 사건 기록(사건을 누르면 그 베일 또는 배치 팝업, 따로 된 "사건 상세" 없음), 대시보드의 "이 배치 상세"·최근 차량·베일 줄, 3D 홈의 "이 차량 기록"·"이 배치 상세"·"이 베일 상세".

## 2026-10-16 섹터 지정의 실제 배합
- 문제: "자동 · 섹터 지정" 중에 로봇(장면·로봇 페이지)은 지정 섹터에서만 집는데, 배치는 계속 계획 배합을 보여 주고 기록했다.
- 결정:
  - 서버가 배합 중인 배치에 지정을 건다(`Batch.pinning`). 지정이 한 번이라도 걸린 배치는 실제로 컨베이어에 놓은 **부피(m³)** 비율로 실제 배합(`actualMix`, 정수 %, 합 100)을 계산해 보낸다. 계획(`mix`)은 그대로 두고 화면은 둘을 함께 보여 준다("계획 배합" / "실제 배합 (놓은 부피 기준)", "섹터 지정 중 · A1 · B1" 표시). 지정이 걸린 적 없는 배치는 `actualMix: null`(계획대로)이라 화면이 예전과 같다.
  - 부피로 계산한 이유: 계획은 집기 횟수로 나누지만 한 번에 집히는 양은 더미 높이·등급에 따라 다르다(0.06~0.14 m³). 실제로 압축기에 들어간 양에 가까운 것은 부피다.
  - 지정 시작·변경·해제는 배치 사건 기록(`pin_started`·`pin_changed`·`pin_ended`, 수행자·섹터)과 배치 기록(`pinChanges`: 시각·사람·섹터, 해제는 빈 목록)에 남는다. 지정 중에 새 배치가 배합을 시작하면 같은 지정을 그 배치에도 걸고 사건을 남긴다. 배합이 끝나면(압축) 배치의 지정은 풀리고 기록은 남는다.
  - 지정이 끝나면 **남은 집기**(배치당 집기 횟수 − 이미 놓은 횟수)만 계획 배합비로 나눈다. 지정 중에 생긴 차이를 메우려고 계획을 바꾸거나 더 집지 않는다(사람이 지정한 결과를 서버가 몰래 되돌리지 않게, 배치 시간도 늘지 않게).
  - **평균 수분**: 실제 배합이 있으면 서버가 실제로 놓은 부피로 가중 평균해 `avgMoisturePercent`를 바꾼다. **목표 압력**: 서버가 실제 배합의 수분으로 다시 계산한다(모의 규칙: 계획 목표 + 0.6 MPa × (실제 수분 − 계획 수분), 허용 범위 안으로 자름, `PRESSURE_PER_MOISTURE_MPA`). 단, 사람이 `set_batch_pressure`로 정한 목표 압력은 다시 계산하지 않는다(사람의 결정이 우선). 둘 다 **프론트는 계산하지 않고** 받은 값을 표시만 한다.
  - 베일 상세의 배합 스냅샷은 실제 배합이 있으면 실제 배합(압축된 것)이다.
- 상태: 가정(확인 필요: 서버 담당 — 실제 배합을 부피로 셀 수 있는지, 수분·압력 재계산 규칙, `docs/questions.md` B33). 명세 6절 "로봇팔 7단위"에 적었다.

## 2026-10-17 출하 마당: 지게차가 생산을 따라가고, 칸이 차면 압축기가 기다린다
- 문제: 3D 홈에서 베일이 마당에 쌓이다 겹쳤다. 지게차 한 대가 입고(배출구 → 칸)와 출하(칸 → 화면 밖 26m)를 모두 맡아 한 개에 70초쯤 걸렸고(시연은 52초, 모의 서버는 약 60초에 하나), 칸은 12개뿐인데 가득 차면 0번 칸에 덮어 놓았다. 장면 베일은 14개까지만 만들어 그 이상은 패널에만 있었다.

- 상태: 세 층·표 하나는 확정(2026-10-17 사용자 요청). 표의 역할별 권한은 가정(확인 필요: 대표님 A4·A13, 서버 담당 B35~B39).

## 2026-10-17 3D 화질 기본값은 모두 high, 측정이 낮으면 내린다
- 바꾼 것: 기본 단계를 기기 종류별(폰 low · 태블릿 standard · 데스크톱 high)에서 모두 `high`로. 접속 때 프레임 측정(`qualityProbe`)이 낮게 나오면 `standard`·`low`로 내리고(코어 4개 이하는 `standard`까지), 설정에서 직접 고른 값이 있으면 그대로 따른다.
- 이유: 모바일 웹에서 성능이 충분한 폰도 저사양으로 시작해 화질이 아쉬웠다(사용자 요청). 이전 규칙은 측정이 기본값에서 한 단계까지만 움직여 폰은 `standard`가 한계였다.
- 주의: 측정이 끝나기 전 1~2초는 `high`로 그린다. 저사양 폰은 그동안 느릴 수 있다. 실기기 측정으로 확인 필요.

## 2026-10-17 터치 기기는 주변 차폐(N8AO)를 끈다, 옛 자동 화질 값은 한 번 버린다
- 아이폰에서 standard·high일 때 로봇팔이 통째로 검게 나왔다(low는 정상, 데스크톱 렌더는 정상). 주소에 `?noao=1`을 붙여 주변 차폐만 끄면 정상이라 N8AO가 원인으로 확인됐다. 폰·태블릿(`pointer: coarse`)에서는 N8AO를 쓰지 않는다. 그림자 지도·빛 번짐 등은 그대로.
- 화질 규칙이 바뀌어도 기기가 예전 자동 측정 값을 기억해 새 기본(high)이 적용되지 않았다. `ecocycle.qualityRule` 버전을 두고, 버전이 다르면 직접 고르지 않은 값은 한 번 버려 다시 잰다.
- 설정의 화질 설명이 폰에서 칸을 넘친 것은 전역 규칙 `label { white-space: nowrap }` 때문이었다. 그 줄에서만 `whitespace-normal`로 푼다.

## 2026-10-17 폰의 기본 홈은 대시보드
- 홈 모드를 고른 적이 없으면 폰(짧은 변 600px 미만)은 대시보드, 태블릿·데스크톱은 3D. 고른 값은 그대로 기억한다. 이유: 폰에서 3D가 무겁고 첫 화면이 느리다(사용자 요청). 폰에서도 상단 바의 전환으로 3D를 고를 수 있다.

## 2026-10-17 3D 카메라: 끄는 동안은 손을 바로 따라온다
- 카메라는 목표를 느슨하게 쫓는다(`GLIDE` 2.3, 약 0.4초). 지역 전환·대상 고르기에는 부드럽지만, 손가락으로 끌 때도 같아서 손이 2만큼 움직여도 화면은 1만큼만 따라왔다(사용자 지적). 끄는 동안(포인터가 눌려 있는 동안)만 `DRAG_GLIDE` 22로 거의 바로 따라오게 한다. 놓은 뒤와 프로그램이 옮기는 전환은 그대로 부드럽다.

## 2026-10-17 설정 글 줄바꿈 바로잡기, 화질 기본 high를 폰에서도 닿게
- 설정의 화질 설명이 폰에서 계속 칸을 넘쳤다. 앞서 `whitespace-normal`을 붙였지만 적용되지 않았다: `styles/index.css`의 `label { white-space: nowrap }`은 Tailwind 레이어 밖(레이어 없는 CSS)이라 레이어 안의 유틸리티 클래스보다 우선한다. 그 줄에서만 `!whitespace-normal`(중요도)로 풀었다. 실제 Chromium 390×844에서 `white-space`가 `normal`이고 설명이 두 줄로 감기는 것을 확인했다. 앞 항목의 "전역 규칙 때문"이라는 원인은 맞고 고침이 틀렸었다.
- 폰이 고화질로 시작하지 못한 이유: (1) 자동 측정이 `high`를 주려면 코어가 5개 이상이어야 했는데 아이폰 같은 기기는 코어 수를 적게 알려 줄 수 있다 → 2개 이하만 `standard`로 막는다. (2) 측정 전 설정 화면은 기억한 값이 없으면 `기본`을 선택된 것으로 보여 주었다 → 기본 표시도 `high`(`loadQualityMode`).

## 2026-10-17 폰에서 가끔 저사양으로 시작: 측정을 한가할 때 두 번, 높은 쪽을 쓴다
- 원인(추정): 자동 측정은 앱이 막 뜨는 동안 한 번만 재고(1.2초) 그 결과를 기기에 저장한다. 이때 프레임이 일시적으로 떨어지면(내려받기·화면 만들기, 저전력 모드) 한 번의 나쁜 값이 `low`로 저장되어 이후 계속 저사양으로 시작한다.
- 바꾼 것: 시작 1.5초 뒤(`PROBE_START_DELAY_MS`) 두 번 재서 높은 쪽으로 고른다. 이전 규칙으로 저장된 값은 `ecocycle.qualityRule` 3으로 한 번 더 버린다. iOS 저전력 모드처럼 기기가 프레임을 30으로 묶는 경우는 실제 값이라 그대로 반영된다.
- 진단 중: 기본 화질 로봇팔 검은색은 빛 번짐(`?bloom=1`)을 켜면 나아지지만 확대하면 일부 남고 고화질에도 남는다. 실시간 그림자를 끄는 `?noshadow=1` 스위치로 자기 그림자 여부를 본다(`Stage.tsx`의 임시 `withDebug`).

## 2026-10-17 자동 화질 기준을 낮춘다: 30프레임 기기도 고화질
- 바꾼 것: 측정 25fps 이상이면 `high`(전: 50), 15fps 이상이면 `standard`(전: 28), 그 아래만 `low`. 코어 2개 이하는 여전히 `standard`까지.
- 이유: 측정은 기기가 정말 느린지와 일시적·전력 모드로 30프레임에 묶인 것을 구분하지 못한다. 30프레임에 묶인 폰도 고화질로 렉 없이 돈다(사용자 확인). 요즘 폰은 대부분 충분하고, 정말 약하면 설정에서 낮춘다. 시작 1.5초 뒤 두 번 재서 높은 쪽을 쓰는 것은 그대로다.
